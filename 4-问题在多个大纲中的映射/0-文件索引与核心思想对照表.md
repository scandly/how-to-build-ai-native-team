# 5-问题在 22 个大纲中的映射 —— 文件索引与核心思想对照表

| 9 | AI独立能力很强，团队怎么协调和提升 | 通过 Mock 沙盒静默契约协作实现协调（大纲 13），通过合并熔炉机制识别冗余微服务并合并再生实现能力提升（大纲 17） |
| 10 | 传统开会拉齐需求？AI Native怎么解决 | 用 Mock 沙盒验证替代传统对齐会议——统筹 AI 生成精确 JSON Schema 契约，所有部门 AI 盲写代码，CDCT 验证在沙盒中替代所有人类会议 |
| 11 | 别人改的把你的冲掉了怎么办 | 通过意图锁和内容寻址哈希链（大纲 14）防止代码覆盖——AI 基于特定基线哈希提交变更意图，引用过期哈希的意图直接被统筹者拒绝 |
| 12 | 人员离职需要交接些什么 | 零损耗交接——系统通过不可变意图快照（大纲 14）、注册契约网络（大纲 1）、CDCT 验证向量实现自我文档化，新人阅读意图宪法并跑通 CDCT 即可接管 |
| 13 | 需求变更或加需求怎么办 | 需求变更即意图演化——人类提交意图修正案，统筹者评估其对契约网络的影响，冲突时触发仲裁模式（大纲 8），销毁旧代码，所有 AI 从新契约重新生成 |
| 14 | 统筹者打基线确定版本时需要做些什么 | 基线即冻结意图拓扑 + 契约网络 + 沙盒验证向量的哈希指纹（大纲 14），而非标签代码文件——任何语言、任何时间生成的代码，通过相同验证即为合法版本 |

| 16 | 某个模块需要更换框架需要做哪些工作 | 目标范围重建 + 影子验证——锁定外部 CDCT 契约不可变，部门 AI 基于原意图快照（大纲 14）用新框架从零重新生成所有代码，镜像流量到新旧沙盒逐字节比对后切换 |
| 17 | 自己一套模型测评工具，定期检查5个部门，作为日报输出 | AI Native 日报通过架构适应度函数（大纲 17）——测量意图纯度分、契约健康度（冗余/反模式）、链路阻力（跨域延迟/Saga 触发率），识别合并熔炉候选，用客观系统熵值替代主观人工汇报 |
| 18 | 耗时工作事前验证 | 高风险耗时操作的影子预演（大纲 13）——AI 自行拦截昂贵操作，在 Mock 沙盒中跑边界值预执行，生成验证报告提交人类审批后获取执行凭证 |
| 19 | 轻量快速试错契约：大纲二十三——画布与铅笔模式 | 双轨契约机制——在正式"铁轨"契约旁引入"铅笔草案"轨道，探索性业务可绕过严格 CDCT 快速擦写，业务模型经线下人工确认后再"着墨为铁" |
